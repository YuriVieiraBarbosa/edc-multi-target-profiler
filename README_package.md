# EDC-QSAR Pipeline — package v2

This package is an **addition** on top of your `pipeline_edc_qsar`, not a replacement. It adds
a reporting layer (consensus v2), the analysis scripts, and the documents produced in the latest
sessions. The 17 scripts at the root are **byte-for-byte copies** of your originals, verified by SHA-256.

## What did NOT change

Before anything else, to avoid misunderstanding:

- **No model was retrained.** The 61 models (18 IC50 + 32 Ki/Kd/EC50 + 11 Tox21) are the same.
- **`predict_edc2.py` has not been changed.** It still produces the `_summary.csv` with the single level
  (high / moderate / low / no alert), exactly as before.
- **No dataset was changed.** The curation, the filters, and the features are the same.
- **The rule of `scaffold_split` remains the original.** It was tested (see
  `documents/fair_test_scaffold_report.md`), but it was not changed: the decision is yours.
- **The preprocessing remains the same.** The `StandardScaler` is still applied to the entire vector of
  2,180 columns in the 10 models that scale, and the `Ipc` descriptor was not transformed.

Consensus v2 is an alternative way to **read** the same votes. Nothing requires using it, and the old
format remains available in parallel.

## Installation

Copy the contents of this package into your `pipeline_edc_qsar` folder, keeping the structure. The
models and datasets are already there and are not included in the package (about 110 MB of `.joblib` and 25 MB of
CSV). After copying, the folder should look like this:

```
pipeline_edc_qsar/
  *.py                      17 original scripts (unchanged)
  requirements.txt
  models_final/             18 IC50 models            (already existing)
  models_layers/            32 Ki/Kd/EC50 models      (already existing)
  models_tox21/             11 Tox21 models           (already existing)
  datasets_*/               curated datasets        (already existing)
  consensus_v2/              NEW  two-axis reporting layer
  analyses/                 NEW  analysis scripts and results
  figures/                  NEW  infographics and generators
  documents/               NEW  reports and guides
  example_panel_ref/       NEW  example output in both formats
```
## Usage

**Original format**, with no changes:

```bash
cd pipeline_edc_qsar
python predict_edc2.py --input molecules.csv --name-col name --out results/run1
```

**Two-axis format** (runs the predictor and then re-aggregates):

```bash
cd pipeline_edc_qsar
python consensus_v2/run_consensus_v2.py --input molecules.csv --name-col name --out results/run1
```

This generates the files from the old format (`run1_detail.csv`, `run1_summary.csv`) **and** the
new ones (`run1_v2_summary.csv`, `run1_v2_endpoints.csv`, `run1_v2_coverage.csv`). If you already have
a `_detail.csv` from a previous run, you can re-aggregate without predicting again:

```bash
python consensus_v2/consensus_v2.py results/run1_detail.csv results/run1_v2
```

> **Warning:** always run from the root of the pipeline and with the default model paths. The
> `predict_edc2.py` identifies each model's layer by the **folder name**, so passing
> `--model-dirs` with an absolute path causes the Tox21 layer to be labeled as ChEMBL and corrupts the votes.
> `run_consensus_v2.py` already takes care of this.

## What consensus v2 changes

| | `_summary.csv` (original) | `_v2_summary.csv` |
|---|---|---|
| Unit of evidence | the model: regression and classification of the same endpoint count twice | the endpoint: 1 piece of evidence |
| Role of each task | both vote equally | classification decides positivity; regression gives the potency with a conformal interval |
| Aggregation | a single level, summing ChEMBL and Tox21 | two axes, never summed |
| Within the axis | fraction of active votes | best evidence and how many endpoints corroborate it |
| Model outside the domain | disappears and dilutes the fraction | `not_assessed` state, with coverage alongside |
| Direction of effect | absent | label coming from the mode of the Tox21 assays |
| Pair with no coverage | no row in the file | row with `no coverage` |

The detailed breakdown, the per-receptor coverage table, and the comparison with the old format are in
`documents/consensus_v2_specification.md`.
## Contents

- **`consensus_v2/`** — `consensus_v2.py` (the re-aggregation) and `run_consensus_v2.py` (shortcut that chains
  the predictor and the re-aggregation).
- **`analyses/`** — `panel_layer_ablation.py` measures what each layer adds to the alert;
  `fair_test_scaffold/` carries the test of the `scaffold_split` rule; `results/` has the tables
  generated by these analyses on the reference panel.
- **`figures/`** — the two infographics (the one for the current pipeline and the one for the v2 architecture), their generators, and
  the JSON with the numbers for the second figure.
- **`documents/`** — `consensus_v2_specification.md`, `edc_qsar_engineering_guide.md`,
  `edc_qsar_report.md`, `consensus_layers_report.md`,
  `fair_test_scaffold_report.md` and the project's `README_original.md`.
- **`documents/code_audit_verification.md`** — item-by-item verification of the code audit:
  what was confirmed in the code, what needs a caveat, and two diagnostics run on the 38
  endpoints (local files in `analyses/results/`, not versioned: `diagnostico_scaffold_split.csv` and `diagnostico_aciclicos_split.csv`).
- **`example_panel_ref/`** — the output of `panel_ref.csv` in both formats, plus the pairwise
  comparison. Used to check whether your installation reproduces the same numbers.

## Decisions still open

None of these have been applied, and all of them depend on you:

1. **Double counting.** `consensus_v2.py` resolves this, but `predict_edc2.py` still counts twice.
   There is no automatic integration between the two.
2. **`scaffold_split` rule.** Measured, not changed. Putting the large groups in the training set improves
   things only slightly (median RMSE −0.018), and the gain comes from the data volume, not the composition.
3. **Probability calibration** (step 2 of the architecture). Until this is done, the probabilities of the two
   axes are not comparable to each other: the thresholds range from 0.11 to 0.40 on Tox21 versus 0.5 on ChEMBL.
4. **Quality-based weights** (step 3). This only makes sense with external validation, which does not yet exist for
   the screening axis.
5. **Divergence of the Tox21 CSVs** relative to `README_models_tox21.csv`. Cause not investigated.
6. **Preprocessing.** Scaling only the descriptors, with `log` or clipping on `Ipc`, would require retraining.
7. **Insulin receptor (IR).** Mentioned in the project scope, still without a layer.
8. **Molecules without a Murcko scaffold** all fall into a single pseudo-group. In Tox21 this is 18% to 23% of
   each assay, and leaves two assays with a degenerate external test. See section 4 of the verification.
## Limitations that come with the package

- The v2 consensus **does not improve accuracy and was not validated by accuracy**. It makes auditable what
  the single level was hiding.
- The `panel_ref.csv` (15 positives and 3 negatives assessed, with the class_label assigned per molecule and not
  per receptor) is a smoke test, not a validation.
- There is no independent ground truth for the screening axis: the Tox21 label is itself the training signal.
  BindingDB validates only the pharmacological axis.
- `pIC50`, `pKi`, and `pEC50` are not the same scale. In `_v2_summary.csv`, read potency by the column
  `potency_by_measure`, which separates the measures, and not only by `pAct_best`.
